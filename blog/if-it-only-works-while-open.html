If it only works while open, it isn’t push

The OS will kill the process. The OEM will be worse. A notification that only works in the foreground is a toast with extra steps and none of the guarantees.

The foreground demo lies

Almost every push implementation works in the demo and fails in the field, for one reason: the demo happens with the app open. The developer taps send, the phone is awake, the app is in the foreground, and the message arrives instantly. Everyone nods. Then the product ships, users do what users do — they close the app, the OS kills it overnight, the token rotates, permissions get denied — and the same pipeline delivers nothing to exactly the users who needed it most: the dormant ones you were trying to bring back.

The failure is silent, which makes it the most expensive kind. A crashed screen produces a report. A failed payment produces a ticket. An undelivered notification produces nothing — no error the user sees, no log anyone reads, just a retention curve that sags for reasons nobody can name. Teams then debate content, timing, and copy, rewriting messages that were never received. The copy was never the problem. The pipe was.

Push has to be built backward from the worst case: app killed, token stale, network absent, permissions half-granted, device a low-end model with an aggressive battery saver. If the design only works when the app is warm and the network is kind, it is not a delivery system. It is a snackbar with a server.

Tokens are inventory, not strings

A push token looks like a string you store once. It behaves like inventory that rots. Tokens rotate on app reinstall, on OS upgrade, on backup restore, and on schedules only the platform knows. A token table that is only ever written to is a museum of dead addresses within months, and every send to a dead token is money and time spent measuring vanity delivery instead of reach.

The lifecycle has four operations, and all four must exist from the first release. Register the token on launch and after every authentication event, because login is often when identity and device finally meet — phone-number sign-in especially, where the account barely exists before verification. Refresh it whenever the platform issues a new one, upserting rather than appending so one device never accumulates a history of ghosts. Persist it encrypted alongside the user, because tokens tied to a device without a user cannot be targeted, and tokens tied to a user without a device cannot be delivered. And prune relentlessly: every unregistered-device response from the provider deletes the row that caused it, automatically, the same day.

Pruning deserves emphasis because nobody does it until delivery rates collapse. Providers tell you exactly which tokens died — invalid registration, unregistered device, stale endpoint — and each of those responses is a work order to delete. A nightly job that processes them keeps the table honest. Without it, broadcast math lies: ten thousand sends with three thousand dead tokens reads as a campaign with weak content instead of a database with rot, and the team optimizes the wrong thing for a quarter.

Preferences ride with the token. A user who muted trip updates but kept payment alerts must survive token rotation with those choices intact, which means preferences hang off the user-device pair, not the token string. Check them at send time, not at schedule time, because the hours between scheduling and sending are exactly when people change their minds.

Topics are not fan-out

Targeting is a product decision with engineering consequences. Sending a live update to a whole audience as individual sends is slow, expensive, and fragile — that is a topic, and topics exist so one publish reaches every subscriber without the backend iterating. Twelve seat updates for one bus should collapse into a single "your bus moved" rather than twelve interruptions that train the user to mute you. The rule is simple: addressable individuals get sends, shared facts get topics, and anything in between gets collapsed before it leaves the server.

Scoping follows the same tenant discipline as everything else. A broadcast to all customers and a scoped send to the booked passengers of one trip are different operations with different blast radius, and the API should make the wrong one hard to invoke. Queue fan-out carries this: enqueue one job per audience, expand to devices at send time against live token and preference state, never against a stale snapshot copied at schedule time. Audiences change between scheduling and sending — passengers cancel, users mute, tokens die — and expansion at send time is what keeps the send honest.

Localization multiplies the matrix. When an audience spans languages, the message is rendered per user at send time from their stored preference, not blasted in one language with apologies. Templating with per-locale strings and per-user variables — name, seat, balance, departure — is table stakes. A French-speaking passenger receiving an English fare notice does not file a bug; they churn, quietly, like everyone churns from push failures.

Data messages sync, notification messages knock

The two message types exist for different jobs, and mixing them because it is simpler is how badges lie. Notification messages exist for the tray: the user is not in the app, the platform renders the alert, and the payload should carry everything the tap needs — the ticket id, the chat id, the deep link — because the app may never warm up before the user decides. Data messages exist for sync: unread counts, badge numbers, silent state repair when the process is dead or dying. They wake the app briefly, do the bookkeeping, and vanish.

Badge counts are the canonical example. The badge must equal the server's unread count at all times, reconciled on every data message and every app launch, because a badge that says three when the inbox says zero teaches the user that your numbers are decorative. Tap handling completes the loop: the tap opens the ticket, the verse, the chat — the exact object — never the home screen. Every tap that lands on home trains one more person to ignore you. Deep-link routing data travels in the notification payload itself so the destination survives even if the app was dead for a week.

Foreground and background handlers are separate code paths with separate duties. Foreground receives an in-app presentation — a banner or an alert the user chose — because a tray notification for something already on screen is noise. Background handlers do the quiet work: persist the event, update the badge, schedule nothing they cannot finish before the OS suspends them again. Both paths log delivery with ticket identifiers from the provider, because without per-message status you cannot distinguish "sent" from "received" from "displayed," and those three words describe three different systems.

Retries respect backoff, loops do not

Quiet hours and retry policy have to respect platform backoff. A naive timer loop hammering the provider turns one failure into rate limiting for the whole project, and rate limiting during an outage is how a delay becomes a blackout. Retries belong in the queue with exponential backoff and a ceiling, ticket-status tracking per message, and read-versus-sent persistence so operations can see what actually happened instead of what was attempted.

When push cannot deliver, the fallback must already exist. Encrypted token storage with validation at registration keeps bad addresses out; device-not-registered cleanup keeps them from accumulating; and for the messages that truly cannot wait — payment confirmations, departure changes — an SMS fallback through a provider carries them when the push token is gone. Push-first with SMS fallback is not two systems; it is one delivery guarantee with two transports, decided per message by urgency and cost.

Local scheduling covers the case the server cannot: reminders that must fire with zero signal. Programs and daily schedules rebuild a local plan capped at the platform's limits — sixty items on iOS, weeks ahead, minutes of lead time — with channels, provisional permissions, and multilingual titles handled on device. No server dependency means the reminder works in a village with no coverage, which is precisely where a reminder matters most. Server push and local scheduling are complements: the server delivers what it knows, the device delivers what only it knows.

Permissions are product, not plumbing

The permission prompt is the highest-leverage screen in push, and most teams ship the system default at first launch and wonder why opt-in sits at a third. Users grant permissions to apps that have already shown value, at moments when the value of notifications is obvious — after booking the ticket, not before onboarding. Provisional permission where the platform offers it lets quiet notifications prove themselves before the user is ever asked. Every denial is close to permanent, so the prompt is spent like budget, once, at the right moment, with the reason visible on the screen behind it.

Permission state must be observable. The backend should know, per device, whether alerts, badges, and sounds are granted, and targeting should degrade gracefully: badge-only where alerts are denied, in-app and email where push is gone entirely. Dual-channel designs — in-app plus email alongside push, as with follow and message flows — survive any single denial. A product that goes silent the moment one toggle flips was never a delivery system.

Founders feel push as retention. Engineering should feel it as infrastructure with a dashboard: registration rate, live-token share, per-message ticket outcomes, prune counts, fallback volume. When retention dips after a release, the answer is often not the feature — it is a permission prompt moved earlier, a rotated token unhandled, or a payload that woke the app and painted nothing. Instrument the pipe, and the dips come with explanations attached. Fail quietly, and you will pay quietly, which is the most expensive way to pay.

What this looks like in production

The same principles wear different uniforms per product. A devotional platform serving villages with poor networks cannot depend on any server at send time, so reminders are scheduled locally from programs and daily schedules — a provider that rebuilds the plan, capped for platform limits, weeks ahead, minutes of lead time, with channels, permissions, and multiple languages handled on device. A transport platform across dozens of cities needs the opposite: a full server pipeline with multicast sends, token arrays, invalid-token pruning, preference checks, queue fan-out to whole audiences or single trips, per-user language rendering, persistence of every send, and real-time emission so the live dashboard and the phone agree.

A ticketing app built on phone-number identity wires tokens to verification itself: fetch and upsert on launch and again after one-time-password confirmation, because that is the moment the device becomes a known user. Foreground handlers present alerts, background handlers do the bookkeeping, and the backend exposes token save, token fetch, and send operations as explicit endpoints rather than hidden side effects. Explicit endpoints are auditable; side effects are where tokens go to die unnoticed.

A rewards platform spanning two languages adds the fallback the guarantee requires: encrypted token storage, strict token validation at registration, per-message ticket tracking, automatic cleanup of dead registrations, push-first delivery with SMS fallback when push cannot reach the user, and read-versus-sent persistence so support can answer "did they get it" without guessing. A collaboration platform doubles the channel instead: follow and message flows send email plus two push transports, with background handlers updating badges from unread counts and taps deep-linking into the exact conversation from a cold start.

None of these share code, and all of them share design. Tokens as rotting inventory with registration, refresh, persistence, and pruning. Targeting expanded at send time. Data messages for sync, notification messages for the tray. Retries with backoff and a fallback transport. Permissions treated as product. The uniforms differ because the constraints differ — zero signal versus thirty cities versus two languages versus a demo that cannot crash. The discipline is identical, and it is the discipline that makes day-30 retention a property of the system rather than a hope about the content.

The tray is the product

Everything the user sees without opening the app — the tray entry, the badge, the lock-screen line — is a product surface with its own design rules, and most teams treat it as a log stream. A tray that shows twelve undifferentiated lines from the same app is not twelve touchpoints; it is one lesson in muting. Group by thread, collapse updates into the latest truth, and make every visible line earn its place: what changed, what it means for this user, what the tap does. Forty legible characters beat four apologetic paragraphs.

Rate-limit per human, not per event. The system may generate fifty notifiable facts a day for an active user; the user should receive a handful, digested. Caps per category per day, quiet hours with timezone-aware delivery windows, and digesting — one evening summary instead of nine interruptions — are what separate a product that informs from one that nags. Every mute is close to forever, so each send spends from a budget the user never agreed to replenish. Teams that count sends as engagement are spending someone else's attention and calling it growth.

Measure by type, not in aggregate. Booking confirmations, price changes, chat messages, and marketing blasts have nothing in common except the transport, and an aggregate open rate hides the one category dragging the channel down. Per-category delivery, display, tap, and mute rates show exactly which stream earns its sends and which should be demoted to in-app or email. When a category's mute rate climbs, the answer is rarely better copy — it is fewer sends, better targeting, or a different channel entirely. The tray is shelf space the user rents you daily. Pay the rent, or get evicted.

Questions to ask before you trust a push pipeline

Six questions expose nearly every weak pipeline. What happens to a message when the app has been dead for a week? How do tokens get refreshed, and what deletes the dead ones — specifically, which job, on what schedule? Is targeting expanded at send time or copied at schedule time? Do taps land on the object or on home? What carries the message when push is denied or the token is gone? And what does the dashboard show — sends, or delivery with per-message status?

A team with crisp answers owns a delivery system. A team that answers with providers and SDK names owns a dependency. Give the pipeline one owner and put delivery on their on-call — shared ownership of push means nobody watches the prune job, nobody notices the token table rotting, and nobody connects the retention dip to the release that moved the permission prompt. Notifications are the tray, the badge, and the tap — the parts of your product the user sees without opening it. If it only works while open, it isn't push.
