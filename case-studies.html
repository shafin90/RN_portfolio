Case Study

Legato — Musician collaboration platform, MVP to production

Legato is where I learned to hold a product calm.

A musician profile, discovery, follow, block, groups, chat, push. Small US team, both stores. My part was the phone as it is — killed app, denied permission, null photo, stale socket, unloaded list — and the server agreeing with it.

I start behind the screen. A wrong order means a wrong partner. A follow with no notice kills the loop. A tap that lands at root kills the reply. A crash in a demo room kills trust. So I work failure first.

Search, I kept honest. Fuzzy name, skill overlap on cleaned tags, nearness by true geography, open-to as hard gate. Faces first, then distance. One query returns ranked. I removed the second sort on the phone — it re-sorted rounded strings and broke the database order. I filtered empty photos at query. No merging on the phone, no extra trips. When you type fast, old requests cancel. When place is denied, browsing stays. When lists load late, they fall back to empty with guards. New arrivals never duplicate your browsing.

Matching, I shipped to Explore. Scores run apart from search so the two never fight. Base with capped skill bonus, intent through casual/serious/professional fit, nearness close/far, activity recent/silent by true last-active time. Teach finds learn, looking-for maps to open-to across jam, band, collaboration, teacher, student. Limited per person with expiry. Precomputed daily and on profile change, cleaned weekly, reads cheap. I put it behind a flag with viewed, dismissed, and refresh paths and funnel, and I fixed the time it scores on — without true activity every score reads active and wrong.

Identity, I kept single. Registration creates user, profile, chat identity, and skills together. No orphans, no race. Google and Apple through the same path, recovery by code. I fixed login and logout sticking navigation, and made startup wait for auth and onboarding before fetching nearby.

Follow, I kept notified without risking the follow — token and email after commit, failure never rolls back the relation. Block, I kept everywhere including search within followers. Chat, I made reconnect clean by disconnecting first and resetting flags, gated delete by capability, kept names straight. Open-to to chat, inbox from profile with back to profile, custom-message entry. My rule for taps: that exact thread, back intact.

State, I moved writes into actions — direct writes threw and took screens. I unified three lists into one with stable dependencies — reload loops and remounts ended, infinite scroll wired. Media, I tracked compression from the camera and settled timestamped uploads with thumbnails — no stretched faces, no stuck states.

Release, I kept shippable while adding. Major SDK and React upgrades with camera, picker, auth, and push intact. Crash reporting with user context from the start, then I burned the queue — thread seen, social activity, connection, null handlers. Tutorial and tour, birthday, location control, loading states.

What stayed with me: unfinished paths behind flags, end-to-end on two phones per release, typed contracts so mobile and API cannot drift. The product held — profile to discovery to follow to chat to push, ordered, scored, notified, back intact — because every failure had an owner before it reached a musician.

Case Study

SRKAN — Devotional platform, steady on weak networks

SRKAN is where I learned to serve people the network forgot.

Villages with intermittent signal, small phones, users who need prayer, programs, and giving to simply work. My part was reading that never needs signal, reminders that fire without a server, and donations a donor can trust on a bad radio.

I start from the morning. Someone opens the app before dawn. Home must show today instantly from what is already there, then refresh quietly without losing scroll. Reading scrolls smooth with steady rows that only redraw when language changes. Audio holds one lock — new playback releases the old — with lock-screen controls that survive calls and Bluetooth drops. Position returns after the system kills the app. Images stay light with cached thumbnails so small phones hold their frame rate.

Reminders, I kept local. The plan rebuilds from programs and daily schedules on every launch, in the language of each program, with quiet permission first so value proves before the prompt. No signal needed. The reminder fires in airplane mode because the schedule lives on the phone.

Finding, I kept per type. Programs by title and place, stories by name and healing, donations by name and transaction — each narrowed by status, featured, branch, currency, and date range at query time. Donations keep a dedicated transaction lookup beside the general search, plus export with the same filters and a currency list for finance. Admin lists that stay small filter where they stand. What the eye sees is what the query asked for, nothing merged on the phone.

Giving, I kept careful. Payment confirmed on the server, never trusted from the client. Status follows the provider through webhooks. Receipts upload for bank transfers that need a human eye, stored away safely. Confirmations and transfer instructions go out by email. A repeated press on a dropping connection finds its first result — one intent, one charge, one receipt. Money in more than one currency freezes its rate at the start so finance never chases drift.

Daily rhythm, I kept truthful to place. Schedules carry sessions with dates and zones, branches carry live and recorded video that fall back to empty shapes instead of breaking the screen. Roles stay narrow — who may publish, edit, or read — with tokens checked and revoked cleanly. Uploads arrive compressed within limits. Contact writes to mail with validation. Tests guard the endpoints that move money and mail.

What stayed with me: design for no coverage, small memory, and a dead process — and the product works everywhere. The donor who presses three times, the reader with no bars, the reminder at dawn — none of them should ever need to think about the network.

Case Study

Govihari — River-boat ticketing, fixed capacity, zero double-sell

The constraint

A boat has fixed capacity. Concurrent load overselling means turning paying passengers away at the dock. Phone numbers are the primary identity (rural users, no email). Guest checkout required. Payments via Razorpay with HMAC verification.

Architecture decisions

Reserve → Pay → Confirm as a state machine. Reserve creates a seat hold with TTL (Redis lock, 10 min). Pay calls Razorpay order creation server-side, HMAC-validates the signature on verification, creates the booking row inside the same DB session as the verified payment — so ticket and money can never disagree. Confirm converts hold → ticket. Failed/expired payments auto-cancel and release the seat. No manual intervention, no stuck inventory.

Guest checkout with idempotency. No user row required. Idempotency key = phone + boat + departure timestamp + seat. Retries on bad network reuse the same key — same transaction, never a new charge. Phone number verified via Firebase OTP; token stored encrypted with user context.

On-device totals matching server. Booking total calculated client-side (base + taxes + fees) and sent with order creation. Server re-computes and asserts equality; mismatch rejects the order. Prevents client-side manipulation and currency rounding drift.

Push tied to verification. FCM token fetched on launch and again after OTP verification — that's the moment device becomes a known user. Foreground handlers present alerts; background handlers persist and badge. Backend exposes explicit endpoints: save-token, get-tokens, send-notification — auditable, not side effects.

Result

Zero double-sells at the dock. Stuck inventory eliminated — every seat either confirmed or released. Guest checkout converts users who would otherwise drop at account creation.

Case Study

KavooGo — Rewards platform, EN/FR Africa, idempotent earning loop

The constraint

English- and French-speaking African markets. Campaign matching on country, city, employment, education, salary, eligibility — with normalized location names across inconsistent inputs. Stripe payments with backward-compatible contract migration. Push with SMS fallback. Earning loop that cannot double-pay on retry.

Architecture decisions

Campaign matching as structured ranking. User profile: country, city, employment band, education level, salary band, eligibility flags. Campaigns target the same attributes. Matching = hard filters (eligible?) + ranked boosts (exact city > same country > adjacent). Location normalization at write time: canonical country/city tables, fuzzy match on input, stored as FK. EL/FR market handled by parallel attribute sets, same ranking function.

Stripe migration without breaking existing users. Existing campaignId flow kept backward compatible. Added direct-amount flow for new campaigns. Webhook handler accepts both event shapes, normalizes to internal schema. Idempotency via Stripe event ID dedup table. Refund, failure, checkout completion, success — all tracked per event. Guest checkout supported via PaymentIntent + SetupIntent for saved cards.

Earning loop: verify, record, reward — idempotent at each step. User completes action → server verifies against campaign rules → records earning with idempotency key (user + campaign + action hash) → triggers reward (wallet credit) in same transaction → pushes notification. Retry on any step replays the same key; wallet credit is a single-row upsert with unique constraint. Double-pay impossible by schema.

Push with SMS fallback. Expo Push with encrypted token storage, token validation at registration, per-message ticket tracking. DeviceNotRegistered cleanup job runs daily. Push-first delivery; on permanent failure (unregistered, invalid), Infobip SMS fallback with same payload rendered to text. Read/sent tracking per message per channel. Per-user language preference (EN/FR) stored with token, rendered at send time.

Result

Campaign matching reliable across noisy location data. Stripe migration zero-downtime. Earning loop idempotent — retries on bad network never double-pay. Push delivery with SMS fallback keeps reach high across unreliable networks.

Case Study

JetExpress — Inter-city bus booking, 30+ cities, per-tenant sync

The constraint

30+ cities, multi-tenant (each bus company is a tenant). Two phones tap the same seat on a bad network — must never double-sell. Offline sales across cities, sync per tenant. Multi-gateway payments per company. Real-time tracking for live trips.

Architecture decisions

Seat lock with Redis + idempotent events. Reserve creates Redis lock with TTL (seat + departure key). Idempotent event log (unique event ID per company) records every state transition. Async queue carries confirmations, receipts, notifications — sale path never blocks on them. Double-tap on same seat: second request hits existing lock, gets immediate "taken" response.

Per-tenant offline sync. Each company's data isolated by companyId in every query, index, cache key, queue. Offline sales write to local SQLite (WatermelonDB) with pending sync flag. Sync worker pulls pending, batches by company, pushes to API with company-scoped auth token. Conflict resolution: server wins on seat state; client re-fetches and re-renders. One company's flash sale never starves another's queue.

Multi-gateway per company. Each company configures its own gateway (PayU, Razorpay, Stripe, mobile money). Order creation routes to correct gateway config. Webhook handler verifies signature per-gateway, dedups via company-scoped event ID. Refunds queued with retry limits; exhausted retries land in dead-letter for ops.

Real-time tracking via Socket.IO. Live trip location broadcast to company-scoped rooms. Admin dashboard sees all companies; company admin sees only their trips. KPIs (bookings, revenue, occupancy) computed per company in materialized views, refreshed per sync cycle.

Result

No double-sells across 30+ cities. Offline sales sync cleanly per tenant. Multi-gateway per company without code branching. Real-time ops visibility at scale.
